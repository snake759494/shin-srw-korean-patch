# 신 슈퍼로봇대전 한글패치 v1.0.11

v1.0.11은 **전투 중 검은 화면 프리징**([#136](https://github.com/snake7594/shin-srw-korean-patch/issues/136),
[#140](https://github.com/snake7594/shin-srw-korean-patch/issues/140),
[#143](https://github.com/snake7594/shin-srw-korean-patch/issues/143))을 고친 긴급 패치입니다.
같은 빌드에 열린 이슈 #126~#135의 텍스트 수정도 함께 들어 있습니다.

프리징을 겪으셨다면 이 버전으로 다시 적용해 주세요. 세이브 데이터는 그대로 쓰실 수 있습니다.

사용자 요청에 따라 에뮬레이터는 실행하지 않았습니다. 대신 원본 디스크에서 추출한
128개 SCEDATA 멤버, 5,355개 BTTMES 메시지, 실행 파일의 UI 테이블, xdelta 왕복
적용 결과를 자동 검사했습니다.

## 프리징 원인과 수정 (#136 · #140 · #143)

제보는 라이딘의 에너지커터·고건소드, 가이킹의 하이드로 블레이저, 19화 데이비드 공격
등 특정 전투에서 화면이 검게 멈춘다는 내용이었습니다.

### 원인 — 전투 메시지 아카이브가 섹터 정렬을 잃었습니다

`BTT/BTTMES.BIN`은 전투 대사를 158개 뱅크로 나눠 담고 있고, 게임은 이 뱅크를
**CD 섹터 단위로** 읽습니다. 원본을 실측하면 이 아카이브는 철저히 섹터에 맞춰져
있습니다.

| | 원본 | v1.0.10 |
|---|---|---|
| 뱅크 포인터 총 개수 | 252 | 252 |
| 그중 2048바이트(섹터) 정렬 | **252 (100%)** | **2 (1%)** |
| 파일 길이 섹터 정렬 | 예 | 아니오 |

한글 대사가 원본보다 길어지면서 뒤쪽 뱅크가 조금씩 밀렸고, 각 뱅크의 시작이
섹터 경계에서 벗어났습니다. 그러면 뱅크를 요청했을 때 데이터가 RAM 버퍼 안의
엉뚱한 위치에 실립니다. 초반에는 밀린 양이 작아 넘어가지만, 밀림이 누적된 뒤쪽
뱅크(15화 이후)에 닿는 순간 전투가 검은 화면에서 멈춥니다. 특정 기체가 아니라
**그 대사가 들어 있는 뱅크**가 문제였기 때문에, 같은 화에서 다른 유닛으로 바꿔도
계속 멈춘다는 제보(#140)와도 맞습니다.

### 수정

재압축한 아카이브도 원본과 똑같이 뱅크마다 섹터 경계까지 0으로 채우도록 했습니다.
패딩은 뱅크 앞이 아니라 **원본이 이미 패딩으로 쓰던 자리**에 넣습니다. 앞에 끼워
넣으면 커진 뱅크가 원본에는 없던 4번째 섹터까지 밀려나기 때문입니다.

| | 원본 | v1.0.10 | v1.0.11 |
|---|---|---|---|
| 섹터 정렬된 뱅크 포인터 | 252/252 | 2/252 | **252/252** |
| 뱅크 스팬 최대 | 0x1800 (3섹터) | — | **0x1800 (3섹터)** |
| 파일 길이 | 346,112 (정렬) | 373,924 (비정렬) | **358,400 (정렬)** |

아카이브 증가분은 12,288바이트(6섹터)이고, 패치 이미지는 오히려 v1.0.10보다
18,816바이트 작아졌습니다.

### 검증

- 빌드된 이미지에서 아카이브를 다시 꺼내 **252개 뱅크 포인터 전부** 섹터 정렬 확인
- 실행 파일 안의 미러 인덱스 테이블이 아카이브와 일치
- 스크립트 점프 8,750곳 중 메시지 중간에 착지하는 것 **0건**
- `qa_issue74.py` 오류 0건, `qa_translation.py` · `qa_issue_followups.py` 통과
- 128개 SCEDATA 멤버 전부 압축 해제 가능, 최대 16,191/16,384바이트

한 가지 덧붙이면, 이번에 `qa_issue74.py`가 인덱스 불일치 2,031건을 보고했는데
검사 도구가 옛 오프셋 모델(패딩을 모르는)을 쓰고 있어서 생긴 오탐이었습니다.
도구가 패딩까지 포함한 실제 배치를 쓰도록 고쳐 0건이 되었습니다.

## 이슈별 조치

### #126 — 유닛 능력창의 지형·실드 값

- 실행 파일의 세 고정 `タイプ` 필드를 `지형`으로 바꿨습니다. 한글 두 글자를
  그대로 4바이트로 쓰면 3바이트 필드를 침범하므로, 기존 8×16 반각 셀의 `지`와
  16×16 글리프 `형`을 조합해 정확히 3바이트를 유지했습니다.
- 실드와 같은 `無/有` 인라인 값은 문자열 풀에 없는 별도 테이블이어서, 실행 파일
  0x70300의 값을 `무/유`로 직접 교체했습니다.
- `타입` 고정 필드와 `무/유` 테이블의 다음 바이트·포인터가 변하지 않는지 빌드 후
  직접 비교했습니다.

### #130 — 전투 시 류세이 이름

전투 대화의 `FC09` 화자명은 일반 대사와 다른 `PILOTNAME` 경로를 사용합니다.
`류세이`를 반각 셀 일부와 16×16 셀 일부로 섞으면 마지막 `이`가 작거나 일본어
글리프처럼 보일 수 있으므로, 이 이름은 전부 일반 16×16 한글 글리프로 인코딩하도록
고정했습니다. 세 글자의 화면 폭은 9 단위로, 소매점 원본의 20 단위 이름 필드 안에
안전하게 들어갑니다.

### #131 — 전투 시 좀비병·병사 이름

맵과 상태창에서 이미 올바르게 보이는 `PILOTFULL` 경로를 건드리지 않고, 전투 HUD의
`PILOTNAME` 경로만 분리해 수정했습니다.

- `류세이`: 전부 16×16 글리프, 9 단위
- `좀비병`: 전부 16×16 글리프, 9 단위
- `병사`: 전부 16×16 글리프, 6 단위

따라서 `병`만 축소되어 보이거나 이름 뒤에 일본어처럼 보이는 작은 셀이 붙지 않습니다.
실제 빌드 파일의 `PILOTNAME` 테이블 인덱스 55, 100, 244를 직접 읽어 예상 바이트와
비교했으며, `PILOTFULL`의 `좀비병`·`병사`도 공용 풀 QA에 포함했습니다.

### #132 — 합체·이벤트 화면

첨부된 7개 화면을 원본 파일까지 역추적한 결과, 화면 위의 `東方不敗は...`,
`全新!! 系裂!! 天驚!! 傲乱!!`, `見よ! 東方は赤く燃えている!!`,
`ガイキング、合体完了!` 등은 SCEDATA/BTTMES 문자열이 아니라 애니메이션·이벤트
프레임에 포함된 비트맵 캡션이었습니다. `MAP/ANIME.DAT`, `MAP/EVENT.DAT`,
`MAP/EVENT2.DAT` 및 작은 그래픽 파일에서 해당 문장의 게임 문자 인코딩을 다시
검색했지만 번역 가능한 문자열 레코드가 존재하지 않았습니다.

따라서 일반 대사 풀을 잘못 늘려 이벤트 포인터를 손상시키는 패치는 넣지 않았습니다.
화면 하단의 실제 대사는 기존 번역 경로로 유지되고, 정적인 공격 연출 캡션은 이번
문자열 패치의 대상 밖으로 분류했습니다. 이 범위 확인 내용을 이슈 댓글에 남겼습니다.
