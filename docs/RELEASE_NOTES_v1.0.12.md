# 신 슈퍼로봇대전 한글패치 v1.0.12

v1.0.12는 전투 대사창의 **파일럿 이름이 일본어로 보이는 문제**
([#137](https://github.com/snake7594/shin-srw-korean-patch/issues/137),
[#130](https://github.com/snake7594/shin-srw-korean-patch/issues/130),
[#131](https://github.com/snake7594/shin-srw-korean-patch/issues/131))의 원인을 없앤 패치입니다.

## 원인 — 이름이 "글자"가 아니라 "원시 바이트"로 저장돼 있었습니다

v1.0.8에서 이름 줄의 폭을 원본에 맞추려고 **압축 코드 페이지**를 도입했습니다.
파일럿 이름에 자주 쓰이는 음절 21개를 실행 파일의 8×16 반각 폰트 칸에 덧그리고,
이름을 그 칸 번호 한 바이트로 저장하는 방식입니다.

그래서 `산시로`는 이렇게 저장됩니다.

```
F4 2E    산   (16×16 한글 글리프)
95       시   (반각 칸 0x95 — 원본에서는 ウ)
49       로   (반각 칸 0x49 — 원본에서는 お)
```

문제는 **`95 49`라는 바이트 자체에는 "한글"이라는 정보가 없다**는 점입니다.
그 두 칸이 한글로 덧칠돼 있어야만 한글로 보입니다. 덧칠이 적용되지 않은 상태로
그려지면 원본 가나가 그대로 나옵니다 — 그게 정확히 제보된 **`산ウお`** 입니다.

실제로 출하 이미지의 반각 칸을 그려서 대조했습니다. 같은 바이트를 v1.0.10 폰트로
그리면 `산시로`, 원본 폰트로 그리면 `산ウお`가 나오고, 제보 화면은 후자와 일치합니다.

이름 데이터를 만드는 단계와 폰트를 덧칠하는 단계는 서로를 검사하지 않았습니다.
둘이 어긋나면 **221개 이름이 한 마디 경고도 없이** 반쪽 일본어가 됩니다.

## 수정 — 필요할 때만 압축 칸을 씁니다

이름을 일반 16×16 한글로 적었을 때 **원본 일본어 이름보다 넓어지지 않으면 그대로
일반 글리프로** 적습니다. 압축 칸은 그렇게 해서는 이름 줄이 넘칠 때만 씁니다.
혼자서도 들어가는 이름이 굳이 두 번째 폰트 뱅크에 의존할 이유가 없습니다.

`산시로`가 여기 해당합니다. 원본 `サンシロ-`가 10단위인데 한글 `산시로`는 9단위라
이제 압축 칸 없이 들어갑니다.

```
이전  F4 2E 95 49        산 + 반각 시 + 반각 로
이후  F4 2E F3 C1 F2 DC  산 + 시 + 로  (전부 16×16 한글)
```

- 압축 칸에 의존하는 이름: **221개 → 140개**
- `아무로`처럼 원본 폭을 지켜야 하는 이름은 그대로 3셀을 유지합니다
  (`qa_issue74.py`가 이 조건을 검사합니다)

빌드에 검사도 추가했습니다. 이름이 만들어내는 모든 최상위 바이트가 알려진
압축 칸인지 확인하고, 아니면 빌드를 세웁니다.

## 알아둘 점

정품 릴리스(v1.0.8 이후) 어느 것으로도 `산ウお`를 만들 수 없다는 것도 확인했습니다.
v1.0.8·v1.0.9·v1.0.10 실행 파일 모두 21개 칸에 한글이 정확히 들어가 있고, 원본
`ウ`·`お` 비트맵은 패치 이미지 어디에도 남아 있지 않습니다. 그래서 제보 화면은
정품 이미지가 아닌 것(패치를 겹쳐 적용했거나 파일이 섞인 경우)일 가능성이 큽니다.

이번 수정은 그 경우에도 `산시로`가 깨지지 않도록 **의존 자체를 없앤** 것입니다.
혹시 계속 같은 증상이 보이면 Track 1의 SHA-256을 알려주세요.

## 전투 프리징(#136 · #140 · #143)에 대하여

v1.0.11에서 전투 메시지 아카이브의 섹터 정렬을 원본과 같게 복원했습니다. 그 자체는
원본이 지키던 규칙을 되살린 것이라 그대로 두지만, **그것이 프리징의 원인이라고
단정할 근거는 아직 없습니다.** 이후 검증에서 CD 로더가 정렬이 어긋난 뱅크도 처리한다는
디스어셈블 결과가 나왔습니다.

전투 텍스트 해석기가 `0xEC~0xEF`를 스크립트 포인터를 전진시키지 않는 죽은 핸들러로
보내는 것은 사실이고 압축 칸 중 `드`(0xEC)·`아`(0xED)가 거기 걸리지만, 이것도 원인으로
확정하지 못했습니다. `아무로`가 `ED 42 49`인데 첫 전투가 정상 동작하기 때문입니다.
추측으로 바꾸지 않고 코드에 근거만 기록해 두었습니다.

프리징이 계속되면 알려주세요. 계속 조사하겠습니다.
